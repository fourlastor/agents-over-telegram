name: telegram-setup
description: Connect this agent or project to Telegram with the Agents over Telegram plugin, reuse the human's existing bot, and guide private local pairing and Codex project setup.

Use this skill for “connect this agent to Telegram” and plugin onboarding. The normal plugin provides skills; setup creates one native project `telegram` MCP entry for a dedicated group or forum topic, using the human's bot registered once. Another agent project reuses that bot and gets its own client/destination. Unrelated bots and bridges stay outside the task. Do not configure a global plugin MCP server or add `AOT_*` launcher settings for this workflow.

## Connect the project

If this skill's installed package includes a root `mcp.json` or `.mcp.json`, it is an advanced rendered profile with its connection already configured. Check that package's scoped `connection_status` and report any loading problem. Do not run the project setup wizard or create an additional native MCP entry. Rendered packages intentionally have no onboarding action; the steps below apply to the normal skills package.

1. Identify the intended project directory and logical label from the current task. When attaching an existing desktop chat, verify its registered project directory; the repository used by its shell commands can differ. Do not infer the MCP configuration directory from the chat label or active repository alone. A project is the scope: all Codex chats in that exact directory share its Telegram identity and permissions. Explain this once; if the user needs separate identities, use separate dedicated project directories. Reuse an existing `.aot-profile.json` in that exact directory; do not search parent projects for a profile or choose an unrelated client by label.
2. Select the runtime without reading credentials. If the exact project already has its native `[mcp_servers.telegram]` entry, prefer that configured `command` and matching profile; ordinary onboarding must not migrate an existing project to a new runtime just because the plugin was updated. Check that the absolute executable is available. If it is missing or conflicts with the profile, report the specific repair needed rather than overwriting configuration or selecting another client.

   For a new project without a configured runtime, locate this installed plugin's bundled `scripts/bootstrap_runtime.py` relative to the skill package. Check for an available Python **3.11+** interpreter, then invoke the script with that interpreter. Do not assume the first `python3` on `PATH` is compatible; check its version and select an installed compatible interpreter if needed. For example:

   ```sh
   "/absolute/path/to/python3.11-or-newer" "/absolute/installed/plugin/scripts/bootstrap_runtime.py"
   ```

   Bootstrap automatically uses uv if available, otherwise Python's `venv`/`ensurepip` and pip inside its private environment. **Do not make uv installation a prerequisite for ordinary setup.** Invoke the default installer mode unless a specific mode is requested. The script returns JSON with `status: "ready"`, `version`, `executable`, `runtime_dir`, `reused` and `installer`; use the returned absolute `executable`. It prepares a stable runtime outside the plugin cache, so do not require a second checkout or assume `${PLUGIN_ROOT}/.venv/bin/aot` exists. If compatible Python or its venv/pip bootstrap support is missing, report that specific requirement; on Debian/Ubuntu the matching `python3-venv` or versioned package may be needed. Link to the official [Python downloads](https://www.python.org/downloads/) or [venv documentation](https://docs.python.org/3/library/venv.html). Do not install globally or fetch another Python/uv installation to bypass a missing prerequisite. Normal online bootstrap may download its pinned dependencies into the private runtime. For requested offline operation, read [runtime details](../../docs/OPERATIONS.md#prepare-the-runtime): uv needs cached dependencies, while a fresh pip installation needs a populated compatible wheelhouse. Existing validated runtimes can be reused.

   Use the selected executable for setup:

   ```sh
   "/absolute/path/returned/as/executable" setup --label Alpha --project-dir "/absolute/path/to/project"
   ```

   Add `--host` for the agent host that will use the project: `codex` (the default) writes the native `.codex/config.toml` entry and approves its `messages_poll`, `message_send` and `messages_ack` tools, `claude` relies on the Claude Code plugin's MCP server, `pi` writes `.pi/mcp.json` and `amp` writes `.amp/settings.json`. Every host also gets a non-secret `.aot-runtime.json` that the host plugins use to start this project's runtime. Use the host you are running in unless the user names another one. Follow the host steps in [agent hosts](../../docs/HOSTS.md#set-up-a-project).

   Reuse the registered account's actual state directory with `--state-dir` when it differs from the default. To attach an existing authorized client, add its file path with `--client-file`; never read or display that file's capability contents. For an already registered account and authorized local setup, run `--prepare-only` to prepare/reuse project files without collecting or sending. Follow the reported next step and skip pairing when already connected. Otherwise give the same command without `--prepare-only` to the human for interactive pairing. First registration belongs in the human's private terminal, including the receiver-ownership assertion; see [pairing details](../../docs/OPERATIONS.md#pair-the-project).
3. For a first bot, guide the human to create it with `@BotFather` and add it to a dedicated group or forum topic; this build does not pair direct messages. The terminal wizard registers or reuses the account, creates or reuses the client, gives an addressed pairing command, collects after the human sends it, and asks the human to review the actual numeric sender/group/topic before confirming. Token entry is hidden. Never ask for a token in chat/tool arguments, read it into model context, or automate the human's destination confirmation. Reuse already-authorized routine setup; do not add a second permission round for the same local work.
4. The wizard prepares `.aot-profile.json` and a single native `[mcp_servers.telegram]` entry in the project's `.codex/config.toml`, preserving unrelated configuration and rejecting conflicts. This is the intended connection; do not add a rendered plugin server as well. The user adds/opens the intended project in Codex and decides whether to trust it. Do not change global trust settings or accept a host trust prompt on their behalf. Reload/reopen the project chat to load its configuration; do not claim the profile is active before checking its tools. In Claude Code, with a plugin version whose launcher relays MCP and with the plugin already enabled in the session, no reload is needed: the Telegram tools appear in the running session within a few seconds after setup writes `.aot-runtime.json`.
5. Call `connection_status` through that project's MCP tools. Report the logical label, actual bot, destination, state and any returned `next_action`. Check that the intended senders are authorized in this connection. Group membership and BotFather privacy/bot-to-bot settings do not grant the plugin's sender permissions; use verified numeric IDs and existing operator authorization for the [sender grants](../../docs/OPERATIONS.md#additional-senders-and-peers). If tools are unavailable, use the [local controls](../../docs/OPERATIONS.md#everyday-controls) to diagnose setup. Never substitute another project's server to make the check pass.
6. After pairing succeeds, ask the owner once whether to turn on owner notifications for this connection. Explain it in one or two sentences: the agent can then send them private pings from this bot, only for things that need them personally, at most 3 per hour and 10 per day, and they must send /start to the bot in a private chat once. Run `"<executable>" --state-dir "<state_dir>" delivery-settings --client-file "<client_file>" --owner-notify on` only on a clear yes, with the paths from `.aot-profile.json` (pass the client file path; never read the file). On a no or no answer, leave it off. See [owner notifications](../../docs/OPERATIONS.md#notify-the-owner-privately).

An existing active bot receiver requires a deliberate owner-coordinated handoff; do not stop it, replace webhooks, or start a competing consumer as routine onboarding. `--receiver-handoff-confirmed` is the human's assertion that the selected bot has no competing receiver, not a bypass for uncertainty.

Setup alone does not authorize Telegram publications or ongoing agent coordination. For status, pause/resume, recent context or explicitly authorized communication, use [telegram-coordinate](../telegram-coordinate/SKILL.md). Intake is on demand; setup does not install a daemon or start listening. If the user explicitly asks to listen, follow the normal-launch listener in [telegram-coordinate](../telegram-coordinate/SKILL.md) and [desktop listening](../../docs/DIRECT_DISPATCH.md). ChatGPT opens from the app list as usual; do not configure a custom launcher, `CODEX_CLI_PATH`, a WebSocket backend override or a protocol wrapper for ordinary setup or listening. Use the exact authorized local chat and the requested lifecycle. A continuous or restart-after-login request is not a request for the default 55-second check; follow the coordinate skill’s continuous-listening procedure.

## Connect in Claude Code without a restart

When the user asks to connect a project from Claude Code, never ask them to restart Claude Code. Tell them up front what, if anything, they will have to type.

1. If the plugin is missing, install it for the user with `claude plugin marketplace add fourlastor/agents-over-telegram` and `claude plugin install agents-over-telegram@agents-over-telegram --scope user`. If it is installed but disabled, enable it with `claude plugin enable agents-over-telegram@agents-over-telegram` and the scope `claude plugin list` shows.
2. If this session started without the plugin (step 1 changed something, or no `telegram` MCP server and no Agents over Telegram hooks are loaded), ask the user to type `/reload-plugins` once: `/reload-plugins --force` in the terminal CLI, plain `/reload-plugins` in the desktop app. That is the only step they type besides pairing.
3. Prepare the runtime and run setup as described above, with `--host claude`. Pairing stays the user's private step in their own terminal.
4. Check the connection. When the plugin's `connection_status` tool is available, call it; the tools appear by themselves within a few seconds after setup. When it is not (the desktop app connects a newly added plugin MCP server only in the next session), run the same tools from a shell in the project folder: `"<executable>" tool connection_status`, `tool messages_poll`, `tool message_send` and `tool messages_ack`, with JSON arguments on stdin, where `<executable>` is the path in the project's `.aot-runtime.json`. They follow the same rules as the MCP tools. Hook notices repeat this command when it is needed.

## Update a Claude Code project to a newer version

Use this only when the user asks to update Agents over Telegram. Ordinary onboarding never moves a configured project to another runtime.

1. Update the plugin with `claude plugin update agents-over-telegram@agents-over-telegram`, adding `--scope` to match the scope `claude plugin list` shows for it.
2. Run `scripts/bootstrap_runtime.py` from the newest installed plugin version with a Python 3.11+ interpreter, as in first setup, and take the returned `executable`.
3. Read `state_dir` and `label` from the project's `.aot-profile.json`. Never read the client file. Run `"<executable>" --state-dir "<state_dir>" setup --label "<label>" --project-dir "<project>" --host claude --prepare-only`. This rewrites `.aot-runtime.json` to the new runtime and keeps the client, its pairing and its allowed senders. It must report the project as connected, with no pairing command. If it reports anything else, stop and tell the user.
4. In Codex, after installing or updating the plugin, run `aot codex-hooks`. If it reports `needs_approval`, ask the user to approve AOT's hooks in the ChatGPT desktop app, or with `/hooks` in the Codex CLI in the project. Codex asks again after every plugin update. Hooks and the wake waiter use the new runtime from their next event. With a plugin version that relays MCP, the `telegram` MCP server moves to the new runtime before its next tool call, and Claude Code refetches the tools. Changed hooks, skills or monitors in the plugin itself need `/reload-plugins` in the terminal CLI, or a new session in the desktop app. A session that started on a plugin version without the relay needs `/reload-plugins` (terminal CLI) or a new session once, to start the relay.
5. Call `connection_status` and report the new version, if it shows one, and the connection state.

This path is for Claude Code. Codex, Pi and Amp store the runtime command in their own project configuration, and setup refuses to replace a different `telegram` entry there.
